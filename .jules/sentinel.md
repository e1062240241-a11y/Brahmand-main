## 2024-08-14 - Information Exposure in Exception Details (CWE-200)
**Vulnerability:** Across multiple FastAPI routing endpoints, internal system errors, library-specific tracebacks, subprocess std err contents, and unhandled exception strings (`str(e)` or `str(exc)`) were directly embedded in `HTTPException` detail fields and returned to clients on 400 and 500 status codes.
**Learning:** This widespread pattern leaked sensitive diagnostic information (e.g., failed API keys, binary paths, Cloud Vision structures, database errors) to potentially malicious users. The pattern existed because developers sought easy diagnostic feedback on the client side without implementing a dual logging approach (logging internally + generic client messaging).
**Prevention:** To prevent this, never embed raw exception details (`str(e)`) or stack traces into `HTTPException` responses. Instead, log the actual exception using `logger.exception()` or `logger.error()`, and return a generic, sanitized error message (like "An internal server error occurred") to the user.
